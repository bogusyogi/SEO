# Repository support & activation

This matrix describes executable repository capability, not an activated portfolio.
Private site/account mappings belong outside this public repository.

| Route | Delivered behavior | Qualification / next step |
|---|---|---|
| Original skill knowledge | All 94 historical file paths retained; edited guidance reconciled | Static lineage in `MIGRATION-COVERAGE.md`; not every historical sentence is unchanged |
| Portfolio collection | Isolated roots, provider failures, cadence, receipts, repeat-safe ticks | Deterministic providers; authenticate each live provider separately |
| Literal HTML repair | Approved source, baseline conflict checks, public title/description/H1 assertions | Real local queue + simulated HTTP |
| Native SSR source | Host-proposed TSX/template changes with explicit public assertions | Source is not executed by verifier; site's normal build/preview remains required |
| Supporting files | Up to nine companions plus primary source in one GitHub tree/PR | Same site/kind/target, approval binding, interrupted application recovery |
| Shared repository apps | Site-local policy paths mapped through `repository_subdir` | Configure exact app directory & distinct deployment environment |
| Robots/sitemap/link changes | Explicit response assertions for approved source values | Positive assertions; arbitrary redirects, removals & application behavior require a specifically qualified check |
| Content/media | Source/author/editorial policy, staged immutable assets, public asset checks | Two-site fixtures exercise content/media; host factual & preview review must be real |
| GitHub publication | Exact reviewed tree, separately approved merge, exact deployment receipt | Protocol fixtures; configure existing pipeline's receipt producer |
| Recovery | Queue rollback resumes after interruption; reverse PR restores original source files | Remote recovery needs normal merge/deploy/verification |
| Follow-up | Due page-filtered GSC job, bounded retries, descriptive outcomes | Fixture provider invoked when due; live impact requires elapsed observation time |
| Codex host | Optional read-only `codex exec` proposal wrapper | CLI flags inspected; process protocol fixtures; no real autonomous model run certified |
| Other hosts | JSON request/submit or trusted wrapper contract | Qualify chosen host's actual tools, permissions & preview capability |
| Browser-only rendering / transformed media | No automatic assertion of support | Supply site-specific qualified verification before unattended use |
| Unknown source/CMS ownership | No guessed adapter or backend write | Resolve actual source repository & authorized deployment route |

Donor repositories informed documented workflow choices and optional adapters.
`DONOR-REVIEW.md` records inspected material and decisions; no exhaustive donor
codebase comparison or universal integration is claimed. Legion is not required.
SellRight remains a backend provider, never an SEO publishing API.

## Executable activation sequence

Use `OPERATIONS.md` to configure each site's identities, policy and read-only provider
credentials; use `doctor --live` to distinguish configuration from authenticated reads.
Use `PORTFOLIO-WORKFLOW.md` for request/submit, publication and reconciliation commands,
`CODEX-HOST.md` for the optional host, and `DEPLOYMENT-RECEIPTS.md` for existing pipelines.

After a site is qualified, an operator's existing scheduler invokes:

```sh
python /opt/SEO/seo.py run --portfolio /private/portfolio.json tick
```

Per-site `.seo/schedule.json` collection jobs accept `interval_seconds`: `604800`
for weekly or `259200` for three days. Pending workflow and outcome jobs advance on
ticks independently of collection cadence, so choose scheduler frequency accordingly.
Neither package installation nor this qualification creates a managed schedule.
